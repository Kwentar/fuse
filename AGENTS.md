# Правила работы с Fuse

Правила действуют самостоятельно, без истории чата. Fuse — один проект: общее Go-ядро, Windows GUI и Android-клиент; документы macOS относятся к тому же приложению.

Все инструкции, требования, задачи и результаты работы, необходимые для сопровождения Fuse, находятся в этом репозитории. Документов должно быть достаточно для работы из отдельного клона.

## Перед началом

1. Прочитай [README](README.md), [REQUESTS](REQUESTS.md), [SPEC](SPEC.md), [BACKLOG](BACKLOG.md) и последние записи [CHANGELOG](CHANGELOG.md) / [RUNLOG](RUNLOG.md).
2. Проверь корень Git, `git status --short --branch`, ветку, upstream и remotes. Если Git ещё не настроен, явно зафиксируй это; не выдумывай историю, remote или результаты синхронизации.
3. При настроенном remote выполни `git fetch origin`; чистую рабочую ветку с upstream обновляй через `git pull --ff-only`. Сохраняй чужую работу, не применяй force push, разрушительный reset и удаление изменений ради синхронизации. При одновременной работе используй отдельную ветку.
4. Найди задачу в `docs/backlog.md`, уточни её источник и отметь «В работе». Проверь, не изменились ли файлы во время работы другого агента.

## Запросы, спецификация и бэклог

Значимые запросы сохраняй в REQUESTS с датой и устойчивым REQ-ID. Доступную исходную формулировку цитируй точно; пересказ и восстановленные сведения помечай явно. Старые запросы не переписывай: уточнения и отмены оформляй отдельными связанными записями. Не сохраняй секреты и всю переписку. Инициативы агента не выдавай за требования пользователя.

SPEC описывает согласованное целевое поведение со ссылками на REQUESTS, а не подтверждает реализацию. Существующие ТЗ в `specs/` сохраняй; новые согласованные уточнения фиксируй в SPEC и связывай с исходными документами. Для мелких исправлений без изменения поведения менять требования не нужно.

Единственный активный список задач — `docs/backlog.md`; корневой BACKLOG служит указателем. У задачи должны быть устойчивый TASK-ID, источник, критерий завершения и статус «В очереди», «В работе» либо «Заблокировано». У блокировки указывай причину и следующий шаг; у частичной задачи — сделанное и остаток. Завершённые задачи переноси в CHANGELOG и убирай из активного списка. Отмены сохраняй со ссылкой на запрос об отмене. Идентификаторы не переиспользуй.

## Особенности приложения

- Ядро: Go 1.27.3, модуль `fuse`; зависимости закреплены в `go.mod` и `go.sum`. Windows GUI — C# WinForms; Android — Java и то же Go-ядро, сборка без Gradle. Команды и инструменты перечислены в README.
- Сохраняй совместимость идентичности, профилей, Android package `org.p2pmessenger.app`, каталога `P2PMessenger`, IPC и сетевых протоколов. Переименование продукта само по себе не является основанием мигрировать эти идентификаторы или создавать новый Peer ID.
- Не удаляй пользовательские ключи, контакты, историю и файлы ради запуска или проверки. Для тестов используй отдельные профили. Сбой чтения ключа не должен незаметно создавать новую идентичность.
- Публичный `internal/config/default-network.json` содержит пустые списки серверов. Настройки своей сети храни локально; перед публикацией проверяй состав исходников и архивов. Файл `.env_server` не нужен клиентской разработке; не открывай и не выводи его без необходимости по явно поставленной административной задаче.
- SSH-скрипты меняют внешнюю инфраструктуру; запускать их можно только в рамках соответствующей задачи пользователя. Обычная правка документов или клиента не требует SSH, изменения firewall или перезапуска серверов.
- В этой папке есть ТЗ macOS, но исходники macOS-оболочки не обнаружены. Расположение уточняй; не создавай замену и не объявляй macOS неподдерживаемой только из-за отсутствия её исходников здесь.
- Требование «новые файлы сверху» относится к спискам файлов в интерфейсе всех клиентов; подробности — в SPEC.

## Проверки и результаты

Используй команды README и проверяй соразмерно изменению. Для сетевых тестов Go на Windows предусмотрен `scripts/test-node.ps1` со стабильным путём тестового EXE. Наличие сборки не доказывает запуск, поведение или работу на другом устройстве. Правки только Markdown проверяй чтением diff, ссылок и согласованности документов; запуск приложения для них обычно не требуется.

В RUNLOG записывай дату, устройство/ОС, версию или коммит, команду/сценарий, результат и непроверенное. Для изменённого дерева указывай базовый коммит и локальные изменения; до первого коммита прямо пиши, что базового коммита нет. Исторические отчёты обозначай как исторические, без приписывания себе новых прогонов. Полные технические логи и тестовые данные оставляй локально.

После содержательного этапа обновляй CHANGELOG: дата, REQ/TASK, изменения, проверки со ссылкой на RUNLOG и ограничения. Частичный результат не называй завершённым.

## Завершение и передача работы

При настроенном Git проверь diff и staged diff на лишние файлы и секреты, сделай осмысленный коммит и push. Если Git/remote отсутствует или отправка не состоялась, явно сообщи, что результат остаётся локальным. Перед созданием GitHub-репозитория установи аккаунт, владельца и URL; пользователь выбрал публичную видимость Fuse, но это не означает, что аудит и публикация уже выполнены.

Незавершённую работу передавай отдельной рабочей веткой с записью в бэклоге: сделано, осталось, ветка, следующий шаг, результат push. Git не передаёт историю чата, зависимости и локальные настройки. При отсутствии Git оставь явную заметку о локальном состоянии.

Подробные инструкции запуска для Windows, Android и macOS поддерживай в README, непроверенное отмечай. При изменении запуска, зависимостей или платформ обновляй README и затронутые документы Fuse. Код, запросы, спека, бэклог и журналы хранятся в приложении.

Не коммить реальные абсолютные пути устройств, секреты, ключи, `.env*` с реквизитами, зависимости, кэши, сборки, технические логи и пользовательские данные. Ссылки на документы Fuse делай относительными внутри репозитория. Локальные настройки устройств исключай из Git.
