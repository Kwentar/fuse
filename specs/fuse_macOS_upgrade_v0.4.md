# macOS: обновление клиента для совместимости с Windows / Android 0.4

Дата: 2026-11-04. Дополнение к `fuse_macOS_TZ_v0.1.md`; при противоречии это задание имеет приоритет. При обновлении существующего Mac-клиента сохранить Peer ID, профиль, контакты и историю. Не создавать новый аккаунт при обновлении.

## Главный сценарий

Передача множества оригинальных файлов — основная функция: выбрать папку или 1000 фото и 10 видео, добавить всю выборку в долговечную очередь, наблюдать прогресс и заниматься своими делами. Не просить разрешения на каждый входящий файл от добавленного контакта. Автоматически сохранять в `~/Downloads/P2PMessenger`, дать один выбор другой папки. В sandbox использовать security-scoped bookmark и сохранять доступ между запусками. Существующие файлы не заменять: суффиксы `(2)`, `(3)` и т. д. Не запускать полученные файлы автоматически.

Файлы любого размера в пределах int64 и доступного диска; 4 МиБ — блок протокола. Не декодировать/пересжимать изображения и видео. Сохранять исходные байты, проверять SHA-256. Не загружать всю выборку или большой файл в RAM. Папки текущего протокола передаются как отдельные файлы, без сохранения дерева; объяснить это в интерфейсе до добавления папки.

## Оболочка

- Отдельный список контактов, чат, вкладка очереди, возможность открыть чат в отдельном окне.
- Множественный выбор, drag-and-drop файлов/папок, Cmd+V файлов из Finder. Текстовый буфер остаётся обычной вставкой текста.
- Перечисление папок и хеширование вне main thread; пропуск симлинков и понятные ошибки отдельных файлов. Частично успешную пачку не считать целиком неудачной.
- Сохраняемая очередь; две одновременно активные отправки — ограничение параллелизма, остальные ждут без ошибки. Пауза/продолжение выбранных задач или пачки. Перезапуск возобновляет незавершённую активную очередь; явно поставленные на паузу задачи остаются на паузе.
- Прогресс каждого файла: подтверждённые и текущие байты, процент, размер, скорость, состояние; общий upload/download. Размеры человекочитаемые: КБ, МБ, ГБ. Отдельные состояния подготовки, очереди, подключения, передачи, восстановления, паузы, доставки и ошибки сохранения.
- Виден маршрут LAN → direct → relay и этап проверки. Не подписывать relay-передачу как P2P/LAN. Выбор маршрута работает в общем ядре.
- Закрытие окна не должно неожиданно обрывать очередь: поддержать фоновую работу и явную команду завершения. Предупредить, если приложение действительно завершается с активной передачей.

## Обновить общее Go-ядро из исходников 0.4

Предпочтительно переносить изменения `internal/node`, `internal/cli`, `internal/config`, а не реализовывать wire-протокол заново. Собирать CLI для macOS и запускать через `Process` с массивом аргументов, без shell. Сохранить прежнее местоположение профиля. Не запускать одновременно два ядра на одном профиле. Перед миграцией сделать локальную резервную копию профиля; не включать её в релиз. Downgrade на старый строгий JSON reader не обещается.

### Файловый протокол 2.1

Новый negotiated protocol ID: `/p2p-messenger/file/2.1.0`. JSON framing, поля и `version:2` **не изменены** относительно `/p2p-messenger/file/2.0.0`. Главное отличие: один Yamux stream обслуживает несколько последовательных операций. Получатель читает следующий framed JSON после ACK до EOF/ошибки/таймаута. Нельзя закрывать stream после первого `status` или `chunk` на 2.1.

Последовательность: `status → resume(offset)`, затем повтор `chunk → ready(offset) → raw binary bytes → accepted(offset+length)`, в конце `finish → stored(size)`. Размер блока ≤ 4 МиБ. ACK `accepted` отправлять только после устойчивого сохранения блока и позиции. `stored` — после проверки полного SHA-256. Не добавлять поля в старые wire-структуры: decoder строгий. После переподключения снова `status`; не доверять позиции из одного локального UI. Все ответы проверять по ID, позиции и границам размера.

Сначала согласовать 2.1; если старый клиент не поддерживает, использовать 2.0 (одна операция на stream). На 2.1 сохраняется выросшее окно Yamux, исчезают повторные handshake и лишний `status` перед каждым блоком. Это не pipelining: следующий chunk идёт после ACK. Relay stream периодически переоткрывается (~30 с), чтобы вновь попытаться выбрать прямой маршрут. Прежние текстовые и route-протоколы не менять.

Новые исходники: `file_session.go`, `file_queue.go`, `file_downloads.go`, изменения `files.go`, `node.go`, control/CLI. Режим старого получателя проверен `TestLegacyFileFallback`.

### CLI / локальный JSON API

Все команды: `messenger --data-dir PROFILE --json ...`. CLI выводит JSON по строке на результат.

| Команда | Назначение |
|---|---|
| `send-files PEER --stdin` | stdin: JSON-массив путей, до 128 за вызов; большие выборки разбить на пачки. Каждая строка ответа — задача либо отдельная ошибка. |
| `queue-file PEER PATH FILE_ID` | Идемпотентное добавление с UUID: повтор того же пути/размера не создаёт дубликат. Для надёжного локального staging. |
| `pause-files --stdin`, `resume-files --stdin` | stdin: JSON-массив ID до 128, отдельный результат по каждому. |
| `download-dir [PATH]` | Получить/сохранить папку автоматического экспорта. |
| `files [PEER]` | Полная очередь/история; старого ограничения последних 100 нет. |
| `status` | `transfers.uploaded/downloaded`: накопленные байты за жизнь процесса; скорость GUI считает по дельте времени. |

В file record добавлены `transferred` (живые байты), `bytes_per_second`, `export_path`, `export_error`. `progress` — подтверждённая позиция. `path` после автоматического сохранения указывает на опубликованный файл. Диск хранит метаданные, живую скорость не восстанавливает. При нулевом размере показывать 100% только для stored/delivered. При перезапуске счётчики скорости обнулять. `publish-file` предназначен только для Android content URI; на Mac не использовать.

## Разобраться со скоростью Mac ↔ Windows

Скорость Mac ↔ Windows необходимо проверять отдельно для Wi-Fi и Ethernet, фиксируя фактический маршрут. Замер одного сочетания устройств не доказывает причину задержек.

Локальный Windows-стенд, реальный поток 10 ГиБ: до оптимизации 64,38 с, после 43,42 с (включая подготовку/подтверждение). Не выдавать loopback за скорость физической сети.

На Mac после разрешения пользователя сравнить обе стороны: чистый TCP throughput на LAN, 2.0 и 2.1 на том же файле; записать маршрут, адреса интерфейсов, RTT, длительность hash/write/ACK, CPU и диск. Проверить влияние VPN и Wi-Fi, не менять системные настройки автоматически. После временного ухудшения сеть должна восстановить скорость без перезапуска приложения. Реальные сетевые проверки выполнять на выделенных тестовых профилях с синтетическими файлами.

## Приёмка

1. Сохранение прежнего ID после обновления/перезагрузки.
2. Windows 0.4 ↔ Mac и Android 0.4 ↔ Mac: текст, пустой файл, >4 МиБ, 10 ГиБ, совпадение SHA-256.
3. Пачка 1010 файлов, смешанные фото/видео, повторяющиеся имена, Unicode, длинные пути, нехватка места; очередь не теряется при перезапуске, UI отзывчив.
4. Drag/drop, Finder Cmd+V, добавление новых файлов при уже активной очереди, пауза/продолжение, отключение сети и восстановление.
5. Автоматическое сохранение без диалога на каждый файл; ранее существующий файл не меняется. Дубликат команды/неопределённый ответ IPC не создаёт повторную задачу при том же UUID.
6. 2.1 ↔ 2.1 и fallback на 2.0; LAN, direct при доступности, relay при невозможности прямого соединения. Не ломать сервер и другие размещённые на нём службы.
7. Выдать `.app`, исходники, инструкцию обновления и фактические измерения с разделением стенда и реальных устройств.
