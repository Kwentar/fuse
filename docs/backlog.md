## TASK-FILES-001 — Новые файлы сверху во всех клиентах

Статус: В очереди.
Источник: REQ-2026-11-09-FILE-ORDER, запрос пользователя от 2026-11-09; [требование в спецификации](../SPEC.md).

Запись запроса: [REQ-2026-11-09-FILE-ORDER](../REQUESTS.md#req-file-order).

Привести списки файлов в клиентах Windows, Android и macOS к единому порядку: новые сверху, старые ниже. Применить к спискам файлов в чатах и общему списку передач.

Критерий завершения: требование реализовано и проверено на каждой платформе, в том числе после обновления списка и перезапуска приложения. Непроверенные платформы явно отмечены; задача остаётся незавершённой до завершения всех проверок.
Следующий шаг: определить временную отметку для сортировки и порядок при равных отметках, затем проверить текущее поведение клиентов.

## TASK-FILES-002 — Отмена отправки

Источник: [REQ-RESTORED-CANCEL](../REQUESTS.md#req-restored-cancel), восстановлено из существовавшего бэклога; исходная переписка здесь не воспроизводится.

- Кнопка «Отменить» для отдельного файла и всей выбранной пачки, включая ожидание подготовки, очередь и активную передачу.
- Отличать отмену от паузы: отменённая задача не возобновляется после перезапуска.
- Останавливать чтение/отправку и освобождать слот очереди; исходный файл пользователя не удалять.
- Предусмотреть согласованную очистку частичного файла получателя и внутренних временных копий. Уже полностью доставленный файл удалённо не удалять.
- Явно отображать итог: «Отменено» либо «Уже доставлено», если завершение успело раньше отмены.

Статус: В очереди. По существовавшему бэклогу в 0.4 кнопка отмены ещё не реализована; сейчас доступны пауза и продолжение.
Критерий завершения: отмена файла и пачки работает на всех перечисленных этапах, после перезапуска не возобновляется, оригиналы сохранены, гонка с доставкой отображается корректно.
Следующий шаг: согласовать поведение очистки частичных файлов и реализовать отмену с проверкой граничных состояний.

## TASK-FILES-003 — Дата и время передачи файлов

Источник: [REQ-RESTORED-TIMES](../REQUESTS.md#req-restored-times), восстановлено из существовавшего бэклога.

- Windows, Android и macOS: показывать дату и время отправки/получения в списке файлов и подробностях задачи.
- Различать добавление в очередь, начало передачи и завершение: ожидание в очереди не считать временем отправки. Для исходящего файла показывать время подтверждения доставки, для входящего — завершения приёма.
- Сохранять отметки в истории после перезапуска. Повторное соединение и продолжение не должны затирать первоначальное время начала.
- Хранить отметки в UTC, отображать в локальном часовом поясе: «Сегодня, 14:32», «Вчера, 18:05», иначе дата и время; в подробностях — полная дата и время.
- Время фиксировать на соответствующем устройстве; не обещать совпадение часов отправителя и получателя. Для незавершённой/отменённой передачи не показывать вымышленное время доставки.

Статус: В очереди. По существовавшему бэклогу отображение этих отметок в интерфейсе пока не реализовано.
Критерий завершения: отметки сохраняются и корректно отображаются на Windows, Android и macOS после перезапуска и возобновления передачи; отсутствующее завершение не заменяется вымышленной датой.
Следующий шаг: сопоставить имеющиеся поля хранения и интерфейса с указанными моментами времени, затем реализовать недостающее.

## TASK-RELAY-001 — Настройка relay-серверов пользователем

Статус: В очереди.
Источник: [REQ-2026-11-09-RELAY](../REQUESTS.md#req-relay), пункт 1.

Дать пользователю возможность задавать relay-серверы, которые использует клиент. Конкретный способ настройки пока не согласован. Текущая ручная настройка описана в [инструкции по relay](relay-servers.md).

Критерий завершения: согласованный способ настройки реализован; клиент использует заданные пользователем relay, инструкция обновлена.
Открытые вопросы: способ ввода и изменения настроек, охват платформ, работа со списком нескольких серверов.

## TASK-RELAY-002 — Обмен своими relay-серверами

Статус: В очереди.
Источник: [REQ-2026-11-09-RELAY](../REQUESTS.md#req-relay), пункт 2.

Дать пользователю возможность передавать другим пользователям параметры подключения к своим relay-серверам, чтобы получатель мог добавить их в свой клиент.

Критерий завершения: пользователь может поделиться relay, а получатель — добавить его и использовать для подключения.
Открытые вопросы: формат обмена и способ добавления. Ссылка, QR-код и текст — возможные варианты для обсуждения, а не согласованные требования.

## TASK-PUBLISH-001 — Подготовить публичный GitHub-репозиторий

Статус: В работе. Публикация только исходников разрешена пользователем; релизы отложены.
Источник: [REQ-2026-11-09-PUBLIC](../REQUESTS.md#req-public), уточнения [PUBLISH-CHECK](../REQUESTS.md#req-publish-check) и [PUBLISH-SOURCE](../REQUESTS.md#req-publish-source).

Сделано: проект переименован в fuse; реальные адреса серверов удалены из публичной конфигурации; приватные данные исключены из текущего состава. Повторный [аудит утечек](security-audit-2026-11-09.md) охватил исходники и старые артефакты; с отчётом публикуемый состав содержит 107 файлов, истории Git в папке нет. Go-тесты, go vet, Windows-сборка и компиляция Android Java прошли ранее на том же коде. Команды и ограничения — [RUNLOG](../RUNLOG.md#run-publication-check). Архив исходников не требуется для публикации через Git.

Сейчас: локальный Git создан, ветка `master`, `origin` указывает на публичный `Kwentar/fuse`; SSH-доступ подтверждён, удалённый репозиторий пуст. Пробел AUDIT-02 закрыт дополнительными исключениями профиля. Релизы отложены, `dist` остаётся локальным; AUDIT-03–04 не входят в публикацию исходников. Лицензия пока не выбрана.
Осталось: проверить фактический индекс и метаданные автора, сделать первый коммит, выполнить push и сверить удалённый коммит.
Критерий завершения: публичный репозиторий доступен по подтверждённому URL, отправленный коммит сверен, локальные данные и секреты исключены, ограничения проверок отражены в RUNLOG.
Следующий шаг: проверить индекс и отправить исходники в `origin/master`.
