# Отчёт о проверках MVP 0.1.0

Историческая сводка MVP 0.1.0, ТЗ редакции 0.2. Тестовые платформы: Windows x64 и Linux x86_64. Go 1.27.3, CGO выключен.

Работают два отдельных Windows-процесса, которые знают только инфраструктуру и Peer ID друг друга. Они получают подписанный контакт через настоящую DHT и обмениваются через публичный relay на VPS. Прямых клиентских TCP-listeners в этом сценарии нет. **Два процесса на одном Windows-компьютере не заменяют приёмку на двух физических Windows-машинах в разных сетях.**

Проверка A04 на двух компьютерах в разных сетях остаётся открытой. Команды для её выполнения приведены ниже.

## Несколько DHT-узлов и разные relay

Временный стенд: B0:14001, S1:14002, S2:14003, три разные Linux-идентичности и каталога. A использует S1, B — S2. Клиенты не имеют прямых TCP-listeners. A без записи B в кеше получает её через DHT и отправляет через S2. После остановки B0 получатель перезапускается, публикует новый больший Seq, A получает его и обменивается в обе стороны. A также перезапускается с оставшимся S1.

Во второй фазе B получает reservations через S2/S1. S2 останавливается; B удаляет потерянный маршрут, перепубликует контакт и принимает новую отправку через S1. Измеренное восстановление: **4,09 сек**. Это укладывается в 60 секунд для данного стенда. Три процесса находились на одном VPS: физическая независимость серверов этим тестом не доказана.

## Сквозная защита

`TestLimitedCircuitNoise` реально получает reservation, создаёт limited circuit, передаёт данные, сверяет RemotePeer с ожидаемым ID и проверяет ID из RemotePublicKey. Единственный включённый secure transport — Noise, muxer — Yamux. Подмена ожидаемого ID отвергается до прикладного обмена. Relay не содержит обработчика chat-протокола и не пишет историю.

Ограничение libp2p v0.41.1: circuit ConnState не возвращает название security protocol. Поэтому доказательство опирается на конфигурацию, реально аутентифицированный конечный ключ и негативную проверку назначения. Захват tcpdump не использовался и не выдаётся за доказательство E2E.

## Ручное завершение приёмки

1. Скопировать `messenger.exe` на второй Windows-компьютер в другой сети; на обоих выполнить `init`, затем `run`. Обменяться только Peer ID, выполнить `find` и `send` в обе стороны; убедиться в route=relay. Повторить с разрешённым исходящим TCP через VPN. Сохранить `status`, версии ОС и результаты без личной переписки.
2. Под вторым обычным Windows-пользователем проверить чтение ключа/истории и доступ к pipe первого пользователя: ожидается Access Denied. С отдельного компьютера попробовать UNC named pipe: ожидается отказ. Не изменять ACL ради прохождения теста.
3. Сменить сеть/VPN без смены каталога. После восстановления исходящего маршрута дождаться readiness до 60 сек, проверить прежний ID и новую **явную** отправку. Старые сообщения сами не отправляются.
4. Для проверки полного диска использовать отдельный тестовый том/VM, а не системный диск. Проверить отсутствие успешного ACK и последующее ручное восстановление.
5. Для дополнительной ручной проверки байтового relay-лимита использовать отдельный временный узел с малым `circuit_bytes_per_direction`; прерванная отправка может дать delivery_unknown. Повторять только явно, проверять единственную запись у получателя.

Полный Definition of Done из ТЗ не заявляется выполненным до закрытия этих аппаратных/операционных проверок. Автоматические результаты сохраняются отдельно от оставшихся пунктов.
