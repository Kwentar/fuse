# GUI и передача файлов 0.4.0

GUI — WinForms Windows x64; ядро Go управляется через локальный IPC. Имя профиля хранится локально, Peer ID соответствует постоянному Ed25519-ключу. Файлы принимаются только от добавленных контактов. Android-клиент использует то же ядро; инструкция в android.md.


## Изменения 0.4

Очередь долговечная, две активные отправки и любое число ожидающих. send-files принимает пачки до 128 путей; GUI разбивает большие выборки автоматически. Окна чатов можно открывать отдельно. Windows поддерживает drag/drop, Ctrl+V файлов и выбор папки; дерево папки разворачивается в отдельные файлы без сохранения вложенной структуры. Входящие автоматически публикуются в выбранную папку, по умолчанию Downloads/P2PMessenger, без замены существующих файлов. Смена папки влияет на новые публикации. На том же диске используется hard link с последующим удалением частной ссылки; между дисками — потоковая копия.

Новый protocol ID `/p2p-messenger/file/2.1.0` сохраняет stream для нескольких операций; framing и version=2 прежние. При отсутствии поддержки — fallback на 2.0. Это сохраняет выросшее окно Yamux и сокращает служебные round trip. На relay stream переоткрывается через 30 секунд для повторной попытки прямого маршрута. После обрыва снова запрашивается status.

В files добавлены transferred, bytes_per_second, export_path, export_error; progress остаётся подтверждённой позицией. status.transfers содержит накопленные uploaded/downloaded. При остановке ядра активная очередь сохраняется для продолжения; явная пауза сохраняется. Входящие принимаются только от контактов. Приложение не открывает полученные файлы автоматически.

Ниже описание базового 2.0, которое остаётся действующим для fallback. Проверки 0.4 — в reports/0.4-validation.md. Сетевые тесты запускать scripts/test-node.ps1 со стабильным EXE; прямой go test создаёт временный путь и может заново вызвать запрос Windows Firewall.
## Выбор маршрута

При smart_routing переиспользуется существующее прямое соединение. Иначе сначала пробуются адреса LAN из mDNS. По аутентифицированному Noise-каналу `/p2p-messenger/routes/1.0.0` стороны обмениваются максимум восемью адресами (version=1, addresses). Этот служебный канал при необходимости использует relay. LAN пробуется повторно с полученными адресами, затем публичные адреса и libp2p DCUtR, затем relay для полезных данных. Прямые попытки ограничены по времени; неудачный выбор кешируется на 30 секунд, чтобы не задерживать каждый блок файла.

Приватный адрес разрешается только для добавленного контакта и подсети локального интерфейса; ключ удалённого узла проверяется Noise. Публичная контактная запись не содержит LAN-адресов. Проброс портов, изменение firewall и UPnP не выполняются. Поддерживается TCP; успешный NAT traversal не гарантирован.

status.routes содержит по Peer ID stage и route. Этапы: trying_lan, negotiating, trying_direct, trying_relay, connected, unreachable, disconnected. Маршруты: lan, direct, relay. Состояние соединения не является проверкой доступности удалённого приложения в реальном времени: обнаружение сетевого обрыва зависит от транспорта.

## Файлы

Протокол `/p2p-messenger/file/2.0.0`: JSON-запрос с version=2, UUID file_id, именем, размером int64, SHA-256, действием status/chunk/finish, offset, length, chunk_sha256. Один chunk не больше 4 МиБ, общий размер не ограничен настройкой приложения. После ready следуют бинарные байты блока, затем ACK accepted с устойчиво сохранённым offset. Повторное соединение начинается со status. finish подтверждается stored только после проверки полного SHA-256. Передача пустых файлов поддерживается.

Получатель использует сгенерированный путь, не имя из сети. Состояние SHA-256 и прогресс сохраняются после fsync данных; незавершённый хвост отбрасывается при повторе. Подтверждённые блоки не передаются повторно. Нет буферизации всего файла в RAM. После восьми последовательных сетевых ошибок задача приостанавливается; её можно продолжить вручную. При возобновлении отправитель заново проверяет SHA-256 исходного файла.

CLI: contacts; add-contact ID NAME; files [ID]; send-file ID PATH; pause-file FILE_ID; resume-file FILE_ID. send-file возвращает созданную задачу, а не обещание доставки. История файлов хранится в каталоге профиля files. Файлы принимаются автоматически от добавленных контактов, пока есть место на диске; управления квотой и удаления через GUI пока нет.

## Проверки 2026-11-04

- Все Go-тесты; 20 МиБ с проверкой байтов и SHA-256; продолжение после перезапуска получателя.
- Реальная передача 10 ГиБ между локальными узлами: 68,2 секунды с подготовкой и подтверждением, без сравнения с производительностью интернета.
- LAN выбран первым при наличии адреса локального интерфейса; статус меняется после закрытия соединения.
- Два отдельных Windows-процесса через действующий VPS: текст и файл 32 МиБ, SHA-256 копии совпал. Повторено с включённым smart_routing и недоступными прямыми адресами: fallback выбрал relay, файл доставлен.
- GUI: запуск, создание постоянного ID, выход в сеть, визуальная проверка основных элементов.
- Два физических компьютера в разных сетях и NAT traversal — ручная приёмка, пока не выполнена.

Повторяемые проверки: `go test ./...`; `P2PM_LARGE_TEST=1` с `go test ./internal/node -run TestTenGiBEndToEnd -v -timeout 25m`; `scripts/gui-integration.ps1` проверяет публичный relay без изменения сервера.
