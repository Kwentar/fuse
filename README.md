# fuse

fuse — P2P-мессенджер для текста и передачи оригинальных файлов. Windows GUI 0.4.0 / Android 0.4.2 preview / macOS 0.4.1; общее ядро 0.4.1.

В публичных исходниках нет преднастроенных bootstrap/relay-серверов. Перед использованием настройте собственные узлы по [инструкции](docs/relay-servers.md): Windows и macOS — в `config.json` профиля после `init`; Android — в `internal/config/default-network.json` перед сборкой.

Для совместимости сохранены каталог профиля и загрузок `P2PMessenger`, Android package `org.p2pmessenger.app`, macOS bundle ID `app.p2pmessenger.macos`, имена сетевых протоколов и консольного ядра `messenger`. Обновление названия не требует создавать новый ID.

Windows: `dist/fuse-0.4.0-windows.zip`. Android: `dist/android/fuse-0.4.2-preview-arm64.apk`.

Это пути результатов локальной сборки. Сейчас публикуются только исходники; готовые сборки и GitHub Releases пока не выкладываются. Go-тесты, go vet, Windows-сборка и компиляция Android Java выполнены при подготовке исходников; границы проверки — в [RUNLOG](RUNLOG.md#run-publication-check). Прежнее название — P2P Messenger.

## Подготовка окружения

Все команды ниже выполняются из корня приложения, если явно не указано иное. Установите Go 1.27.3 в PATH либо разместите portable Go в `.tools/go`; сам SDK не входит в Git. PowerShell-скрипт окружения задаёт локальные GOPATH/GOCACHE:

```powershell
. .\scripts\go-env.ps1
go version
go mod download
```

Команды приведены по существующим скриптам; на этапе подготовки документов они не запускались. Для Android задайте `-JavaHome` и `-SdkRoot` либо подготовьте расположение `.tools/android`, описанное в его инструкции. Не создавайте новый ключ подписи для обновления установленного приложения с сохранением данных.

Собственные bootstrap/relay настройте по [инструкции](docs/relay-servers.md). Windows читает `config.json` профиля; Android использует настройки, упакованные при сборке. Личные адреса и реквизиты не должны попадать в публичный архив; пустая исходная конфигурация не предоставляет работающие серверы автоматически.

## Запуск на Windows (PowerShell)

Сборка GUI и ядра:

```powershell
pwsh -File scripts/build-gui.ps1
.\dist\windows-0.4\messenger.exe init
```

Для нового профиля заполните `bootstrap_nodes` и `relay_nodes` в его `config.json` собственными адресами по инструкции выше, затем запустите:

```powershell
.\dist\windows-0.4\fuse.exe
```

Рядом с `fuse.exe` нужен `messenger.exe`. Существующий профиль не удаляйте и новый ключ вместо прежнего не создавайте. Запуск из готового архива описан в «Быстром запуске» ниже.

## Запуск на macOS

Нужны Command Line Tools со Swift и SDK macOS, Go 1.27.3. Из корня клона:

```sh
scripts/setup-go-macos.sh  # либо установите Go 1.27.3 самостоятельно
scripts/build-macos.sh
open "dist/macos-0.4.1-arm64/Fuse.app"
```

Для нового профиля можно нажать «Создать ID» в приложении или выполнить `"dist/macos-0.4.1-arm64/Fuse.app/Contents/Helpers/messenger" init`. Затем заполните `bootstrap_nodes` и `relay_nodes` в `~/Library/Application Support/P2PMessenger/config.json` по [инструкции](docs/relay-servers.md) и перезапустите подключение. Пустая публичная конфигурация сама не выводит новый профиль в сеть.

При обновлении завершите прежний P2P Messenger/Fuse через ⌘Q, затем откройте новую `.app`. Прежние ID, профиль и папка загрузок сохраняются; новое имя не требует переноса данных. Сборка использует локальную ad-hoc подпись, без Developer ID/notarization. Подробные команды, параметры архитектуры, резервное копирование и проверки — [macOS build](docs/macos-build.md). Сборки остаются локальными и не публикуются в Releases.

## Быстрый запуск

1. Windows: закройте старое приложение, распакуйте архив целиком в постоянную папку и запустите `fuse.exe`. Рядом нужен `messenger.exe`. Работающий старый экземпляр автоматически не завершается.
2. Android: установите APK поверх предыдущей версии, не удаляя приложение и его данные. Подпись и package сохранены, ID остаётся прежним.
3. На новом устройстве создайте ID, обменяйтесь им и добавьте друг друга в контакты. Аккаунт локальный; ID привязан к постоянному ключу профиля, сохраняется после перезапуска и перезагрузки.
4. Откройте чат. Windows: выбирайте много файлов, папку, перетаскивайте файлы или вставляйте скопированные в Проводнике через Ctrl+V. Android: «Фото и видео» открывает галерею с множественным выбором; «Файлы» — файловый диалог. Можно поделиться файлами из галереи в fuse.
5. Входящие автоматически сохраняются в `Загрузки/P2PMessenger`; папку можно изменить один раз. Каждый файл подтверждать не нужно. Совпадающие имена не заменяют существующие файлы.

Оба приложения должны работать; получатель должен добавить отправителя. В Windows закрытие основного окна сворачивает приложение в трей, передачи продолжаются; полный выход — через меню значка. «Отдельное окно» открывает выбранный чат отдельно.

## Очередь и большие файлы

В очередь можно добавлять новые пачки во время передачи. Две отправки работают одновременно, остальные ждут. Пауза/продолжение доступны в очереди. При перезапуске незавершённая активная очередь продолжается, явная пауза сохраняется. Windows не копирует исходники: не перемещайте и не изменяйте их до доставки. Папки передаются как отдельные файлы без сохранения дерева.

Искусственного лимита размера нет. 4 МиБ — блок, не файл. Реально проверены 10 ГиБ общим ядром; время подготовки включает чтение SHA-256. Android создаёт внутреннюю исходящую копию для надёжного продолжения: нужно свободное место размером с выбранные файлы. После доставки её можно удалить из меню задачи, оригинал в галерее остаётся. При приёме Android временно требует место и под частную копию, и под публикацию в Downloads. Приложение не сжимает и не перекодирует фото/видео; запрашивает исходный формат у системного provider.

Виден маршрут **локальная сеть → напрямую → relay**, общий upload/download, прогресс и скорость каждого файла. Прямой доступ зависит от сети/NAT; relay используется при невозможности прямого соединения. Версия 0.4 переиспользует stream между блоками и совместима со старым файловым протоколом 2.0.

## Первый запуск Windows

Из каталога с `messenger.exe`, обычным пользователем:

```powershell
.\messenger.exe init
.\messenger.exe run
```

`init` выводит постоянный Peer ID. Передайте его собеседнику внешним доверенным способом. На втором компьютере выполните те же команды. Держите `run` открытым. Во втором окне PowerShell:

```powershell
.\messenger.exe status
.\messenger.exe find <PEER_ID_СОБЕСЕДНИКА>
.\messenger.exe send <PEER_ID_СОБЕСЕДНИКА> "Привет"
.\messenger.exe history <PEER_ID_СОБЕСЕДНИКА>
```

Вместо `<PEER_ID_СОБЕСЕДНИКА>` вставьте выданный другим клиентом ID. Новые входящие сообщения показываются в окне `run`. `Ctrl+C` завершает узел. История и `id` доступны после его остановки.

По умолчанию данные находятся в `%LOCALAPPDATA%\P2PMessenger`. Все команды поддерживают `--data-dir PATH`. Для второго независимого экземпляра на одном компьютере укажите другой каталог. Один каталог допускает только один сетевой процесс.

```powershell
.\messenger.exe --data-dir C:\Users\YOUR_USER\P2P-Test init
.\messenger.exe --data-dir C:\Users\YOUR_USER\P2P-Test run
```

`init` копирует настройки из встроенного `internal/config/default-network.json`; в публичной версии списки серверов пусты. Существующая конфигурация и ключ повторным `init` не заменяются. Чтобы использовать свои узлы, измените отдельные массивы `bootstrap_nodes` и `relay_nodes` в `config.json`, затем запустите клиент заново. Формат элемента: `/ip4/IP/tcp/PORT/p2p/ID` или `/dns4/NAME/tcp/PORT/p2p/ID`.

Консольный профиль с `smart_routing=false` не открывает TCP-listener по умолчанию. GUI включает `smart_routing=true` и локальное обнаружение. Приложение не меняет Windows Firewall, UPnP, VPN или маршруты ОС. Нужен исходящий TCP к relay и DHT. `direct_listen_addrs` задаёт адреса прослушивания; `allow_private_addresses` разрешает локальные тестовые адреса и по умолчанию выключен.

## Команды и доставка

| Команда | Результат |
|---|---|
| `init`, `id` | Создание/чтение постоянного Peer ID |
| `run` | Долгоживущий сетевой процесс с локальным IPC |
| `status` | Bootstrap, DHT, reservations, публикация, адреса и эффективные лимиты |
| `find ID` | Подписанная контактная запись через `GetValue`, Seq и источник |
| `send ID "текст"` | Новое сообщение, новый UUID v4 |
| `send ID --stdin` | Многострочный UTF-8 текст из stdin, максимум 64 KiB |
| `retry UUID` | Повтор сохранённого сообщения с исходными полями |
| `history [ID] --limit 50` | Локальная история и текущие статусы |
| `peers` | Известные пиры, роли и фактические соединения |
| `version` | Версия приложения, Go и сведения о сборке |

`--json` даёт машинный вывод; история — JSONL. Переносы строк и табуляция в обычном выводе сохраняются, прочие управляющие символы отображаются как escape-последовательности. Для текста, совпадающего с флагом CLI, используйте разделитель `--` либо `--stdin`.

`delivered` означает ACK `stored`/`duplicate` от аутентифицированного приложения получателя после сохранения, а не прочтение человеком. `not_sent` означает отказ до начала записи фрейма. `delivery_unknown` означает, что запись могла состояться, но подтверждение не получено. `rejected` — явный отказ получателя. `pending` — текущая локальная попытка, не очередь офлайн-доставки.

При `delivery_unknown` используйте выданный Message ID в `retry`. Повтор подтверждённого сообщения сетью не отправляется. Автоматической повторной отправки нет. После потери IPC проверьте `history`: клиент сообщает созданный ID и не повторяет запрос незаметно. Тайм-аут не доказывает, что адресат офлайн.

Коды завершения: **0** успех; **2** неверный ввод; **3** сетевой отказ до передачи; **4** неопределённая доставка; **5** явный удалённый отказ; **6** локальная ошибка состояния, хранения или прав. Сетевой бюджет `send`/`retry` — до 30 секунд вместе с IPC. Поиск — 6 секунд, прямой dial — 2, relay dial — 10, запись — 5, ACK — 5 секунд, в пределах общего deadline.

## Хранение и права

```text
identity.key       приватный Ed25519-ключ libp2p
config.json        версия конфигурации 1
state.json         постоянный монотонный Seq
peer-cache.json    проверенные Envelope и адреса инфраструктуры
messages.jsonl     append-only журнал сообщений и статусов
node.lock          системная блокировка, освобождаемая ОС
logs/              только время, коды событий и Peer ID
```

Windows DACL явно выдаёт доступ владельцу. Проверяется владелец и отсутствие разрешений посторонним обычным пользователям; SYSTEM/Administrators допускаются при проверке. Управление — named pipe с DACL владельца; go-winio v0.6.2 создаёт его с `FILE_PIPE_REJECT_REMOTE_CLIENTS`. Имя зависит от SID и полного пути каталога. Права `0600` не используются как замена Windows ACL. Небезопасный каталог, повреждённый ключ или состояние вызывают отказ; новый ключ автоматически не создаётся.

История и ключ **не зашифрованы на диске**. Администратор, SYSTEM и вредоносный процесс с правами владельца находятся за пределами этой защиты. Для резервирования остановите `run` и копируйте **весь каталог данных** с сохранением прав. Восстановление одного ключа без согласованного Seq/истории, перенос идентичности и одновременные клоны не поддерживаются. Удаление/редактирование истории может разрушить дедупликацию.

ACK отправляется после `Sync`. При ошибке записи новые успешные ACK прекращаются; сетевой процесс сообщает `STORAGE_ERROR`. Частичный хвост журнала сохраняется в `messages.jsonl.tail-<time>`, после чего валидная часть восстанавливается. Повреждение завершённой строки останавливает запуск. Незавершённые исходящие попытки после аварии становятся `delivery_unknown` без повторной отправки.

Технический журнал: максимум 3 файла по 10 MiB, без текстов сообщений, ключей, payload и внешней телеметрии. Явный пользовательский вывод чата и локальная история содержат сообщения. Индекс истории хранит смещения, хеши и статусы; тексты читаются по запросу, ответы IPC ограничены отдельными фреймами.


Артефакты: `dist/messenger.exe`, `dist/bootstrap-node`. Для сетевых тестов нужны разрешённые локальные TCP-сокеты. Для Windows ACL тесты запускаются обычным пользовательским токеном, без ограниченного токена песочницы.

Внешние интеграционные тесты используют только стандартный Python и готовый клиент:

```powershell
# Для сборки с настроенными собственными relay:
python scripts/integration.py
python scripts/integration.py --soak-seconds 905
```

Для SSH-сценариев дополнительно используется локальная Python-библиотека Paramiko 3.5.1 в `.tools/python`. `server_check.py` читает `.env_server` только внутри процесса, не печатает реквизиты и выполняет лишь `printf`/`uname`. Ключ SSH-сервера закрепляется при первом контакте в `.local/ssh_known_hosts` (TOFU). `multinode.py` создаёт три временных systemd-процесса только бинарника проекта и убирает их после проверки. Этот административный тест запускайте только на своём сервере с согласованными свободными портами 14001–14003.

## Публичный Linux-узел

Пример конфигурации — `configs/bootstrap.example.json`, unit — `deploy/bootstrap-node.service`. Укажите настоящий публичный IP в `announce_addrs`; `203.0.113.10` в примере является заполнителем. Публичный DHT/relay использует `/p2pm`, `MaxRecordAge=36h`, TCP 4001, без HTTP API и хранения переписки.

Сервис запускается непривилегированным `DynamicUser=p2pmessenger`, данные — `/var/lib/p2pm-bootstrap/data`, бинарник и конфигурация — `/opt/p2pmessenger/`. Вложенный `data` необходим из-за symlink, создаваемого systemd для DynamicUser StateDirectory. Оператор обеспечивает доступность только необходимого P2P-порта. Скрипт первичного развёртывания отказывается перезаписывать существующие пути; он не устанавливает пакеты, не меняет firewall и не перезапускает чужие сервисы.

Relay: reservation 1 час, circuit 1 час, 16 MiB **в каждом направлении**, 64 reservations, 1/Peer ID, 32/IP, 64/ASN, 4 circuits/пир. Resource Manager: клиент 128 соединений/256 потоков, сервер 256/1024. Chat: 32 одновременных потока всего, 2/пир, 10 новых сообщений/с с burst 20. Продление reservation не обновляет лимит уже открытого circuit.

## Ограничения прототипа

Оба участника должны быть онлайн. Нет серверной офлайн-доставки, централизованных аккаунтов, восстановления ключей, групп и звонков. Текстовые сообщения не повторяются автоматически; файловая очередь поддерживает возобновление. Один VPS остаётся единой точкой отказа. Несколько процессов на одном VPS подтверждают работу протокола без одного bootstrap, но не устойчивость к потере всего сервера.

Шифрование и аутентификация выполняются между конечными клиентами поверх circuit. Relay наблюдает сетевые метаданные; DHT раскрывает подписанные контактные маршруты. Анонимность, защита от Sybil/Eclipse, DDoS, вредоносного ПО и администратора ОС не гарантируются. Любой аутентифицированный пир может попытаться отправить сообщение: адресной книги/allowlist в MVP нет. Seq упорядочивает известные версии, но не доказывает свежесть подписанной записи. VPN использует маршрутизацию ОС; kill switch и отсутствие IP-утечек не обещаются.

Доказательства и ограничения проверок перечислены в отчёте приёмки. Этот релиз — проверяемый прототип, не заявление о промышленной готовности.

## Публикация исходников

Публикуйте подготовленную папку проекта через Git с текущим `.gitignore`. Перед первым коммитом проверьте список добавленных файлов и staged diff; затем настройте подтверждённый remote и выполните push. Проверка текущего состава и ограничения записаны в [RUNLOG](RUNLOG.md#run-publication-check); результаты повторного аудита — в [отчёте об утечках](docs/security-audit-2026-11-09.md).

Архив не требуется. `scripts/package-source.ps1` остаётся необязательным способом экспорта исходников; он требует пустой сетевой конфигурации и исключает локальные настройки, отчёты, ключи, профили, кеши и готовые сборки.

`.env*`, `.local/`, `.tools/`, `dist/`, `docs/reports/` и приватные настройки исключены через `.gitignore`. Исключены также характерные записи передач, принятые файлы и временные записи профиля в произвольных каталогах; сами профили храните вне исходников либо в `.local/`. Не загружайте рабочую папку целиком через веб-интерфейс: он не применяет `.gitignore`. В старых артефактах `dist` подтверждены прежние адреса серверов. Они остаются локальными и не блокируют публикацию исходников; если публикация бинарников понадобится позже, их нужно пересобрать и отдельно проверить.
